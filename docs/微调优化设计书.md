## 1. 背景与目标

### 1.1 现状

当前问数项目是一套 **RAG（检索增强）+ LangGraph 多节点 Agent** 系统，通过「元数据知识库（表/字段/指标/字段值）+ 向量召回 + 多步 LLM 调用」将自然语言转换为可执行 SQL。核心链路如下：

```
用户问题
  → extract_keywords（jieba 分词 + LLM 关键词扩展）
  → recall_column / recall_metric / recall_value（向量/全文召回）
  → merge_retrieved_info（合并召回）
  → filter_metric / filter_table（LLM 裁剪候选集）
  → add_extra_context（补充口径/时间/方言上下文）
  → generate_sql（LLM 生成 SQL）
  → validate_sql / correct_sql（校验 + 纠错）
  → execute_sql（只读执行）
```

当前 LLM 通过 `app/agent/llm.py` 统一调用 `deepseek-chat` 官方 API，各节点用 `prompt/*.prompt` 模板拼接检索上下文后调用。

### 1.2 痛点

1. **通用模型对私有 schema 的映射不稳定**：字段名（如 `order_amount` vs「销售额」）、枚举值（如「华北」vs `region_name`）依赖检索与 prompt 对齐，长尾/别名场景易错。
2. **指标口径无约束**：通用模型易重解释 GMV/AOV 等指标口径，去重、分子分母、时间口径常出错。
3. **澄清能力弱**：缺少时间范围/统计粒度时，通用模型倾向于"猜一个默认值"而非主动澄清。
4. **多表 join 路径与条件遗漏**：复杂 join、having、分组粒度易出错。
5. **安全/方言约束靠 prompt 兜底**：只读、方言适配强依赖 prompt，不可保证。
6. **数据出域风险**：调用云端 API 时业务 schema 与问题外泄，无法私有化部署。

### 1.3 微调目标

对齐 `问数微调.md` 4.2 节六项能力，微调一个**私有化部署的 Text2SQL 专家模型**，替换现有通用 LLM：

| 编号 | 能力 | 目标 |
|---|---|---|
| 4.2.1 | 业务问题到字段映射 | 准确把业务概念映射到表、字段、枚举值、时间字段 |
| 4.2.2 | 字段值识别与标准化 | 把别名/简称/口语映射为标准字段值，识别模糊值是否需要澄清 |
| 4.2.3 | 指标口径理解与计算 | 正确生成聚合、计算公式、分子分母、去重、时间口径 |
| 4.2.4 | 查询意图澄清 | 缺少时间范围/粒度/口径/条件时主动澄清 |
| 4.2.5 | 多表关联与查询条件生成 | 正确生成 join/where/group by/having/order by |
| 4.2.6 | SQL 安全与方言适配 | 只读查询、方言适配、规避危险函数与越权 |

## 2. 现有架构与保留原则

### 2.1 技术栈

| 层 | 组件 |
|---|---|
| API | FastAPI 0.128（`app/api/`，当前为空，待补齐） |
| Agent 编排 | LangGraph 1.0（StateGraph + Runtime context） |
| LLM 调用 | LangChain 1.2（`init_chat_model`） |
| 向量库 | Qdrant 1.16（字段/指标向量集合） |
| 全文检索 | Elasticsearch 8（字段值 ik 分词索引） |
| 元数据/业务库 | MySQL（`meta` 库 + `dw` 库，asyncmy + SQLAlchemy 2.0） |
| Embedding | BAAI/bge-large-zh-v1.5（HuggingFace 本地服务，维度 1024） |
| 分词 | jieba 0.42 |

### 2.2 Agent 图结构（`app/agent/graph.py`）

12 个节点，一条主链 + `validate_sql` 条件边：

```
START
 └─ extract_keywords ─┬─ recall_column ─┐
                      ├─ recall_metric ─┼─ merge_retrieved_info
                      └─ recall_value ──┘         │
                                        ┌─────────┴─────────┐
                                   filter_metric      filter_table
                                        └─────────┬─────────┘
                                             add_extra_context
                                                  │
                                             generate_sql
                                                  │
                                             validate_sql ──(无 error)──▶ execute_sql ──▶ END
                                                  │
                                            (有 error) correct_sql ──▶ execute_sql
```

### 2.3 分层与数据流转

```
app/
├── api/                 # API 层（待补齐）
├── agent/               # Agent 编排层
│   ├── graph.py         #   StateGraph 定义与边
│   ├── state.py         #   DataAgentState（可变状态）
│   ├── context.py       #   DataAgentContext（固定依赖）
│   ├── llm.py           #   LLM 客户端（★ 微调接入点）
│   └── nodes/           #   12 个节点
├── services/            # 业务层（MetaKnowledgeService.build 构建知识库）
├── repositories/        # 持久层（mysql/es/qdrant）
├── models/              # 数据模型（mysql/es/qdrant）
├── clients/             # 各存储/Embedding 客户端管理器
├── conf/                # 配置模型（app_config/meta_config）
└── scripts/             # 构建脚本（build_meta_knowledge.py）
```

- **State（可变）**：`query`、`keywords`、`sql`、`error`、`recall_columns` 等，在节点间传递。
- **Context（固定）**：`dw_mysql_repo`、`meta_mysql_repo`、`value_es_repo`、`column_qdrant_repo`、`metric_qdrant_repo`、`embedding_client`。

### 2.4 现有 LLM 调用点清单

微调模型的**接入面**即下表这些 LLM 调用点，全部保持节点与 prompt 结构不变：

| 节点 | Prompt 文件 | 输入 → 输出 | 状态 |
|---|---|---|---|
| `recall_column` | `extend_keywords_for_column_recall.prompt` | query → JSON 字段名数组 | ✅ 已实现 |
| `recall_metric` | `extend_keywords_for_metric_recall.prompt` | query → JSON 指标概念数组 | ⏳ 待实现 |
| `recall_value` | `extend_keywords_for_value_recall.prompt` | query → JSON 取值候选数组 | ⏳ 待实现 |
| `filter_metric` | `filter_metric_info.prompt` | query+候选指标 → JSON 指标名数组 | ⏳ 待实现 |
| `filter_table` | `filter_table_info.prompt` | query+候选表字段 → JSON 表字段对象 | ⏳ 待实现 |
| `generate_sql` | `generate_sql.prompt`（+可选 `plan_sql.prompt`） | query+上下文 → SQL 文本 | ⏳ 待实现 |
| `correct_sql` | `correct_sql.prompt` | query+SQL+错误 → 修正 SQL | ⏳ 待实现 |

### 2.5 架构保留原则（本设计的硬约束）

1. **图结构不动**：12 节点、边、条件边完全保留；不新增/删除编排节点（澄清能力复用现有 `generate_sql` 前置语义或通过输出契约实现，见 4.4）。
2. **State/Context 类型不动**：`DataAgentState`、`DataAgentContext` 字段不破坏性变更（仅允许新增可选字段以承载微调中间产物）。
3. **Prompt 文件复用**：`prompt/*.prompt` 作为微调指令模板的一部分保留，训练与推理共用同一套指令风格，保证"训练—推理"分布一致。
4. **RAG 检索链不动**：Qdrant/ES/Embedding/jieba 召回逻辑不变，微调模型只消费"检索后的上下文"，不替代检索。
5. **分层不动**：API / Agent / Service / Repository / Model / Client 六层职责不变。
6. **改动只发生在两处**：`llm.py`（模型后端可切换）+ 新增独立的微调子系统（`app/finetune/`，旁路模块）。

## 3. 总体方案

### 3.1 方案概览

采用 **单基座模型 + 统一多任务指令微调（Multi-task Instruction Tuning）**：

- **一个微调模型**覆盖 2.4 节全部 7 类 LLM 调用点的能力，推理时替换 `llm.py` 指向的模型实例。
- **LoRA/QLoRA 高效微调**，保留基座权重，训练与部署成本可控。
- 新增**旁路子系统**（不侵入主链路）：数据采集 → 数据合成/标注 → 训练 → 评估 → 模型版本管理。

```
                       ┌──────────────────────────────────────────┐
                       │           现有主链路（保持不变）              │
  query ──▶ LangGraph ──▶ ... ──▶ llm.py ──▶ [ 微调模型 ] ──▶ SQL
                       │              ▲                             │
                       └──────────────┼─────────────────────────────┘
                                      │ 推理后端切换（OpenAI 兼容 / vLLM）
        ┌─────────────────────────────┼─────────────────────────────┐
        │  旁路微调子系统（新增 app/finetune/，可独立启停）              │
        │  trace 采集 ─▶ 样本仓库 ─▶ 数据合成/标注 ─▶ QLoRA 训练        │
        │  ─▶ 离线评估 ─▶ 模型注册 ─▶ 灰度切换                          │
        └────────────────────────────────────────────────────────────┘
```

### 3.2 微调模型定位

| 项 | 说明 |
|---|---|
| 定位 | Text2SQL 领域专家模型，替代 `llm.py` 中的通用 `deepseek-chat` |
| 覆盖任务 | schema_linking、value_standardization、metric_resolution、clarification、sql_generation、sql_correction（映射见第 4 章） |
| Embedding | 保持 BAAI/bge-large-zh-v1.5 **不变**，微调仅作用于生成模型 |
| 与检索的关系 | 检索负责"海选"，微调模型负责"精筛 + 生成"，二者职责不重叠 |

### 3.3 技术选型

| 项 | 主选 | 备选 | 理由 |
|---|---|---|---|
| 基座模型 | Qwen2.5-Coder-14B-Instruct | Qwen2.5-Coder-7B-Instruct、DeepSeek-Coder-V2-Lite-Instruct | 中文强、SQL 生成 SOTA、Apache-2.0 可商用 |
| 微调方式 | QLoRA（4bit NF4 + LoRA） | 全参 SFT（资源充足时） | 单卡 24G 可训 14B，成本最低 |
| 训练框架 | LLaMA-Factory | transformers + peft + trl | 内置多任务/混合数据集、评估、导出 |
| 部署推理 | vLLM（OpenAI 兼容接口） | SGLang | 高吞吐、兼容 `init_chat_model` 的 openai provider |
| 数据版本 | DVC / 本地目录 + 元数据表 | — | 样本可追溯、可复现 |

## 4. 能力与子任务映射

统一多任务指令模板（训练与推理共用）：

```
【任务类型】{task}
【上下文信息】
数据表信息：{table_infos}
指标信息：{metric_infos}
字段值信息：{value_infos}
时间信息：{date_info}
数据库环境：{db_info}
【用户问题】{query}
【输出】
```

> 说明：`{task}` 与现有 `prompt/*.prompt` 语义一一对应，训练数据按同一指令风格构造，推理时仍走现有 prompt 文件，避免训练/推理分布漂移。

### 4.1 业务问题到字段映射（4.2.1）

- **子任务**：`schema_linking`（对应 `recall_column` + `filter_table`）
- **输入**：query + 召回到的候选表/字段（含 name/role/description/alias/examples）
- **输出**：`{"表名": ["字段1", ...]}`（与 `filter_table_info.prompt` 输出契约一致）
- **训练重点样本**：别名映射（销售额→order_amount）、角色字段区分（dimension/measure/foreign_key）、时间字段识别。

### 4.2 字段值识别与标准化（4.2.2）

- **子任务**：`value_standardization`（对应 `recall_value`）
- **输入**：query + 候选字段值（含标准值 + 同义词/别名）
- **输出**：`{"标准值": [...], "需澄清": [...], "映射": {"别名": "标准值"}}`
- **训练重点样本**：口语→标准值（iPhone→某商品名）、缩写→全称、模糊值澄清判定。

### 4.3 指标口径理解与计算（4.2.3）

- **子任务**：`metric_resolution`（对应 `recall_metric` + `filter_metric`）+ `sql_generation` 中的聚合段
- **输入**：query + 候选指标（含 description/relevant_columns/alias）
- **输出**：`{"选中指标": [...], "口径": {"指标": "聚合函数/分子/分母/去重/时间口径"}}`
- **训练重点样本**：GMV（sum）、AOV（sum/sum 去重口径）、时间口径（自然月/滚动窗口）。

### 4.4 查询意图澄清（4.2.4）

- **子任务**：`clarification`
- **接入方式（保留架构）**：不新增编排节点；在 `generate_sql` 内部先判定"信息是否充分"，充分→输出 SQL，不充分→输出澄清问题 JSON。
- **输入**：query + 检索上下文
- **输出**：`{"need_clarify": true, "questions": ["具体可回答的澄清问题..."]}` 或 `{"need_clarify": false, "sql": "..."}`
- **训练重点样本**：缺时间范围、缺统计粒度、指标口径歧义、筛选条件缺失四类。

### 4.5 多表关联与查询条件生成（4.2.5）

- **子任务**：`sql_generation`（对应 `generate_sql`）
- **输入**：query + 裁剪后的表/字段 + 指标口径 + 主外键关系
- **输出**：单条完整 SQL（纯文本，无 Markdown 代码块）
- **训练重点样本**：多表 join 路径、where/having、group by 粒度、order by、子查询。

### 4.6 SQL 安全与方言适配（4.2.6）

- **子任务**：`sql_generation`（安全约束内化）+ `sql_correction`（对应 `correct_sql`）
- **输入**：query + 上下文 +（纠错时）错误 SQL + 错误信息
- **输出**：只读、符合 MySQL 8.0 方言的 SQL；纠错时保持业务语义不变的最小修复
- **训练重点样本**：危险 SQL 反例（含 INSERT/UPDATE/DELETE/越权表）→ 只读等价改写或拒绝；方言差异（函数名、日期函数）。

### 4.7 能力→节点→子任务总表

| 能力 | 节点 | 子任务 | 输出契约 |
|---|---|---|---|
| 4.2.1 | recall_column / filter_table | schema_linking | 表字段 JSON |
| 4.2.2 | recall_value | value_standardization | 标准值/澄清 JSON |
| 4.2.3 | recall_metric / filter_metric | metric_resolution | 指标+口径 JSON |
| 4.2.4 | generate_sql（前置判定） | clarification | 澄清问题 JSON / SQL |
| 4.2.5 | generate_sql | sql_generation | SQL 文本 |
| 4.2.6 | generate_sql / correct_sql | sql_generation / sql_correction | 只读方言 SQL |

## 5. 训练数据体系

### 5.1 数据来源（四类）

| 来源 | 说明 | 占比建议 |
|---|---|---|
| A. 知识库模板合成 | 基于 `conf/meta_config.yaml` 的表/字段/指标/别名/值，程序化枚举 + LLM 扩写生成 | ~50% |
| B. 历史真实查询 | 从问数系统埋点采集真实问题 + 最终 SQL + 中间检索结果（trace） | ~20% |
| C. 人工标注 | 业务专家标注难例、澄清样例、危险反例 | ~20% |
| D. 开源语料迁移 | 精选开源 Text2SQL 数据（如 Spider、BIRD 中文子集）改造为统一 schema | ~10% |

### 5.2 统一训练样本 Schema

每条样本一个 JSON 对象（多任务共享同一 schema，`task` 字段区分）：

```json
{
  "id": "sample_uuid",
  "task": "sql_generation | schema_linking | value_standardization | metric_resolution | clarification | sql_correction",
  "source": "synthetic | trace | human | open",
  "ability_tags": ["4.2.5", "4.2.6"],
  "database": "mysql",
  "dialect": "mysql 8.0",
  "context": {
    "table_infos": [
      {
        "table": "fact_order",
        "role": "fact",
        "description": "订单事实表，记录订单数量和金额等核心指标。",
        "columns": [
          {
            "name": "order_amount",
            "type": "decimal",
            "role": "measure",
            "description": "订单金额。",
            "alias": ["销售额", "订单金额", "收入"],
            "examples": [1999.0, 299.0]
          }
        ],
        "primary_keys": ["order_id"],
        "foreign_keys": {"customer_id": "dim_customer.customer_id", "date_id": "dim_date.date_id"}
      }
    ],
    "metric_infos": [
      {
        "name": "GMV",
        "description": "全称Gross Merchandise Value，表示所有订单的成交金额总和。",
        "relevant_columns": ["fact_order.order_amount"],
        "alias": ["成交总额", "订单总额"]
      }
    ],
    "value_infos": [
      {"column_id": "dim_region.region_name", "value": "华北", "aliases": ["华北地区", "北区"]}
    ],
    "date_info": "2025-01-01",
    "db_info": "MySQL 8.0，只读账号"
  },
  "instruction": "将用户问题转换为只读 SQL（严格使用上下文中的表与字段）。",
  "input": "华北地区销售总额",
  "output": "SELECT SUM(o.order_amount) AS 销售总额 FROM fact_order o JOIN dim_region r ON o.region_id = r.region_id WHERE r.region_name = '华北';",

    "difficulty": "easy | medium | hard",

  }
}
```

```json
{
  "task": "sql_correction",
  "input": "2025年各地区平均销售额",
  "context": { "sql": "SELECT region_name, AVG(order_amount) FROM fact_order WHERE year = 2025 GROUP BY region_name;", "error": "Unknown column 'year' in 'where clause'" },
  "output": "SELECT r.region_name, AVG(o.order_amount) FROM fact_order o JOIN dim_region r ON o.region_id = r.region_id JOIN dim_date d ON o.date_id = d.date_id WHERE d.year = 2025 GROUP BY r.region_name;"
}
```

### 5.4 数据合成与标注规范

1. **合成管线**：以 `meta_config.yaml` 为事实底座 → 按表/字段/指标/值枚举组合 → 模板生成自然语言问题（含别名、口语化改写）→ 规则引擎或基座模型生成标准 SQL → 执行校验（`explain`/实际执行）→ 通过者入库。
2. **危险反例**：对安全任务，构造含 `INSERT/UPDATE/DELETE/DROP/越权表/危险函数` 的坏样例，标注正确输出为"只读等价改写"或"拒绝 + 说明"。
3. **澄清样例**：系统性地删除时间/粒度/口径/条件中的一项，构造信息不完整问题，标注澄清问题。
4. **质量门槛**：所有 SQL 样本须通过「可执行 + 结果集非空 + 只读 + 方言合法」四重校验；`quality=rejected` 的样本不得进入训练集。
5. **难例挖掘**：定期从线上 trace 中挑选"最终执行失败/被人工纠正"的样本回流标注。

### 5.5 数据规模规划

| 子任务 | 最小可用 | 目标 | 说明 |
|---|---|---|---|
| sql_generation | 2000 | 8000+ | 核心任务，样本最多 |
| sql_correction | 1000 | 3000 | 错误需真实或仿真构造 |
| schema_linking | 1000 | 3000 | 复用 sql_generation 的 schema 侧标注 |
| value_standardization | 800 | 2000 | 依赖字段值字典 |
| metric_resolution | 800 | 2000 | 依赖指标定义 |
| clarification | 500 | 1500 | 澄清问题需人工把关 |
| **合计** | **~6100** | **~20000+** | |

### 5.6 运行时数据采集（埋点）

在 LangGraph 节点中通过 `runtime.stream_writer` 与日志旁路采集 trace（**不改变节点返回值与边**）：

```json
{
  "trace_id": "uuid",
  "thread_id": "session",
  "query": "华北地区销售总额",
  "nodes": [
    {"node": "recall_column", "input": {...}, "llm_output": {...}, "latency_ms": 120},
    {"node": "filter_table", "input": {...}, "llm_output": {...}},
    {"node": "generate_sql", "input": {...}, "llm_output": "SELECT ..."},
    {"node": "execute_sql", "result": [...], "error": null}
  ],
  "final_sql": "SELECT ...",
  "execution_error": null,
  "user_feedback": null
}
```

- 采集开关由配置控制（`app_config.yaml` 新增 `finetune.trace.enable`），默认关闭，避免影响线上性能。
- 采集数据异步写入样本仓库（MySQL `trace_record` 表或对象存储），离线转为训练样本。

## 6. 微调训练方案

### 6.1 基座与适配方式

- 基座：**Qwen2.5-Coder-14B-Instruct**（BF16 权重约 28G，量化后可单卡训练）。
- 方法：**QLoRA** — 4bit NF4 量化基座 + LoRA 适配器（默认挂 `q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj`）。

### 6.2 训练超参（初始建议）

| 参数 | 值 | 说明 |
|---|---|---|
| LoRA rank (r) | 64 | 能力复杂度高，略大 |
| LoRA alpha | 128 | alpha = 2×r |
| LoRA dropout | 0.05 | |
| 学习率 | 2e-4（LoRA） | 余弦退火 |
| warmup | 3% steps | |
| batch size | 128（global） | 通过梯度累积达到 |
| max_seq_len | 4096 | 覆盖长 schema + 多表上下文 |
| epochs | 2~3 | 防过拟合 |
| optimizer | paged_adamw_8bit | |
| 混合数据集配比 | 见 6.4 | |

### 6.3 训练框架与流程

1. 用 LLaMA-Factory（或 `transformers+peft+trl`）加载基座 + 统一指令模板。
2. 数据集按 `task` 分组，配置多任务混合采样权重。
3. 训练产出 LoRA 适配器 + 训练日志（loss、eval loss）→ 注册为模型版本。
4. 评估通过后，合并适配器导出为部署权重，或保留 adapter 由 vLLM 动态加载。

### 6.4 数据配比与去噪

- 权重建议：`sql_generation=1.0`、`sql_correction=0.5`、`schema_linking=0.4`、`metric_resolution=0.4`、`value_standardization=0.3`、`clarification=0.3`。
- 去噪：去除重复样本（按 `input+context` 哈希）、去除 `quality=rejected`、长度/字符集清洗、SQL 二次执行校验。

## 7. 评估体系

### 7.1 评估维度与指标

| 维度 | 指标 | 计算方式 |
|---|---|---|
| 整体可用性 | 执行准确率 EX | 生成 SQL 执行结果与标准 SQL 结果集一致的比例 |
| 4.2.1 字段映射 | 字段精确匹配 / 召回 F1 | 与标准字段集合比对 |
| 4.2.2 值标准化 | 值映射准确率 | 映射值与标准值比对 |
| 4.2.3 指标口径 | 口径一致率 / 结果一致率 | 分子/分母/去重/时间口径与口径库比对，结果集比对 |
| 4.2.4 澄清 | 澄清触发准确率 / 澄清质量 | 应澄清而澄清 + 问题具体可回答 |
| 4.2.5 关联生成 | 结果一致率（含 join） | 结果集比对 |
| 4.2.6 安全方言 | 安全违规率 / 方言通过率 | 写操作、危险函数、越权表的检出 + 语法/方言校验 |

### 7.2 评估集

- **离线评测集**：与训练集隔离（同分布留出 10%~15% + 独立难例集），覆盖六项能力。
- **回归集**：基线模型（通用 `deepseek-chat` / 基座原模型）与微调模型跑同一评测集对比。

### 7.3 离线评估流程

`微调模型 + vLLM → 评测集批量推理 → SQL 执行（沙箱只读库）→ 结果集/口径/安全多维度比对 → 出报告`，未达阈值不予发布。

### 7.4 在线评估与 A/B

- 微调模型与基线模型按流量灰度（`model_routing` 配置），对比 EX、澄清率、人工纠正率、端到端延迟。
- 线上人工标注样本回流，持续迭代。

## 8. 推理接入方案（保留架构）

### 8.1 `llm.py` 抽象层改造（唯一主链路改动）

保持 `llm` 为统一入口，将后端切换为 OpenAI 兼容接口的微调模型（vLLM 天然兼容）：

```python
# app/agent/llm.py（示意）
from langchain.chat_models import init_chat_model
from app.conf.app_config import app_config

def build_llm():
    cfg = app_config.llm
    if cfg.backend == "finetuned":          # 微调模型（vLLM，OpenAI 兼容）
        return init_chat_model(
            model=cfg.model_name,
            model_provider="openai",
            base_url=cfg.base_url,          # http://vllm-host:8000/v1
            api_key=cfg.api_key,
            temperature=0,
        )
    return init_chat_model(                 # 回退：官方 API（灰度/兜底）
        model=cfg.model_name,
        api_key=cfg.api_key,
        temperature=0,
    )

llm = build_llm()
```

`app_config.yaml` 的 `llm` 段扩展：

```yaml
llm:
  backend: finetuned            # finetuned | api（灰度切换）
  model_name: qwen2.5-coder-14b-instruct-lora-v1
  base_url: http://localhost:8000/v1
  api_key: sk-none
```

### 8.2 节点接入

- 所有节点**不修改**调用方式（仍 `prompt_template | llm | parser`），`llm.py` 指向切换后，全链路自动走微调模型。
- 澄清能力（4.4）在 `generate_sql` 节点内通过输出契约分流：解析到 `need_clarify=true` 时经 `runtime.stream_writer` 抛出澄清问题并中断，等待用户补充后重跑（复用现有图，不新增节点）。

### 8.3 vLLM 部署与性能

- 部署：`vllm serve <model> --served-model-name qwen2.5-coder-14b-instruct-lora-v1 --max-model-len 4096`，提供 `/v1` OpenAI 兼容接口。
- 性能：14B 4bit 单卡 A10/3090 可跑，TP 多卡可扩展；`temperature=0` 保证确定性。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 微调后"灾难性遗忘"通用能力 | 口语化/长尾问题退化 | 保留一定比例通用指令数据 + 较小学习率 + 早期停止 |
| 训练数据质量不足 | 学坏 | 四重校验门槛 + 人工抽检 + 难例回流 |
| 检索与生成职责混淆 | 召回差导致模型"编字段" | 训练样本强制"只用上下文字段"，推理保留 RAG |
| 澄清能力误触发/漏触发 | 体验下降 | 澄清样本单独评估，阈值可调，灰度观察 |
| 安全约束被绕过 | 越权/写操作风险 | 安全反例强化 + 服务端只读账号 + SQL 执行前静态校验双保险 |
| 私有化部署资源不足 | 无法上线 | 7B 备选 + 量化 + 批处理优化 |
